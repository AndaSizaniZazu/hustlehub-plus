HustleHub+, explained from the ground up

A walkthrough of the secure login system your sibling built — what it does, why every security decision was made, how to run it on your own machine, and how to prove (with Postman) that it actually works.

01

The big idea

HustleHub+ is a freelance marketplace — think "clients hire freelancers," like a mini Upwork. Freelancers list gigs, clients book them, and the platform tracks the money and estimates tax owed on it.

That's the full vision. Part 1 — the part in this repo — only builds one corner of it: a secure front door. Before anyone can post a gig or book one, they need an account, and that account needs to be hard to steal. So Part 1 is entirely about registration, login, and locking everything behind that login correctly.

Why start here instead of gigs and bookings? Because every later feature — "only freelancers can post gigs," "only you can see your own income" — depends on the system reliably knowing who is making each request. Get that wrong and nothing built on top of it can be trusted.
02

Five ideas that make it secure

Every requirement in the Part 1 brief boils down to one of these five ideas. Once you understand these, you understand the whole assignment.

01Never store the real password

The database only ever holds a hash — scrambled text made from the password using bcrypt, that can't be reversed back into the original. Even if someone stole the whole database, they'd get scrambled goo, not passwords.

const salt = await bcrypt.genSalt(12);
const passwordHash = await bcrypt.hash(password, salt);

02Prove who you are with a token

On login, the server hands back a JWT — a signed, tamper-proof note that says "this is user X." The browser sends it back on every later request instead of the password, in an Authorization: Bearer <token> header.

jwt.sign(
  { id: user._id, role: user.role },
  JWT_SECRET,
  { expiresIn: "1h" }
)

03Never trust incoming data

Every registration/login body is checked before it touches any logic: is the email actually shaped like an email? Is the password long enough? Text fields are also stripped of characters that could be used to inject scripts.

body('email').isEmail()
body('password').isLength({ min: 8 })
body('name').trim().escape()

04Encrypt the whole trip

The API only speaks HTTPS, using a locally-generated SSL certificate. That means the password and token are scrambled in transit — a network eavesdropper sees noise, not credentials.

05Fail without oversharing

Whatever goes wrong internally, the person on the other end always gets the same shape of generic message — never a stack trace, a file path, or "that email doesn't exist" (which would let an attacker fish for real accounts).

res.status(401).json({ message: "Invalid credentials" })
// same message whether the email
// or the password was wrong

04

Run it yourself

Everything below happens inside the backend/ folder, in a terminal.

  1. Install dependencies

    npm install — pulls in Express, Mongoose, bcrypt, and everything else listed in package.json.

  2. Set up .env

    Copy .env.example to .env and fill in a real MONGO_URI (your Atlas connection string) and a random JWT_SECRET. If your database password has an @ in it, encode it as %40 — the URL format breaks otherwise.

  3. Generate a local HTTPS certificate

    Inside backend/certs: openssl req -x509 -nodes -newkey rsa:2048 -keyout localhost-key.pem -out localhost.pem -days 365 -subj "/CN=localhost"

  4. Start the server

    npm run dev — you should see MongoDB connected then Server running on https://localhost:5000.

05

Test it in Postman

The brief asks for proof, not just working code — that's what this section produces.

  1. Turn off SSL verification

    Postman → Settings → General → toggle off SSL certificate verification. Needed because the local cert is self-signed, not from a public authority.

  2. Import the collection

    Drag postman/HustleHub.postman_collection.json onto the Postman window. It appears as HustleHub+ Auth API with three folders.

  3. Run the whole collection

    Click the collection → Run → run Register, then Login, then Protected route, in that order (Login has to run first — it's what generates the token the later requests reuse).

Glossary

endpoint
One specific URL + method the API responds to, e.g. POST /api/auth/login.
middleware
A function that runs before the real route logic — used here for security headers, validation, and the JWT check.
hash
A one-way scramble of data. You can turn a password into a hash, but never turn the hash back into the password.
JWT
"JSON Web Token" — a signed, self-contained proof of identity the server hands out at login and checks on every later request.
HTTPS / TLS
HTTP wrapped in encryption, so data in transit can't be read or tampered with by anything sitting on the network in between.
environment variable
A setting (like a database password) kept outside the code, in .env, so secrets never get committed to git.
status code
The 3-digit number every HTTP response carries — 200 ok, 201 created, 400 bad input, 401 not authenticated.
