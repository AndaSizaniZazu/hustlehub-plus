JavaScript, from zero, using only this project's real code

You don't need to know JavaScript yet to read this. Every idea here is explained once in plain English, then shown immediately in an actual line from the HustleHub+ backend — never a made-up example. By the end, the files in backend/src/ should read like sentences instead of symbols.

01

How JavaScript actually runs here

In a browser, JavaScript runs inside the page. This project doesn't use a browser at all yet — it runs on Node.js, a program that lets JavaScript run directly on your computer, like Python or a compiled program would.

A .js file is just a text file of instructions. When you run:

node src/server.js

Node reads that file top to bottom and executes it. nodemon (what npm run dev actually calls) is the exact same thing, plus one convenience: it watches your files and restarts Node automatically every time you save.

So what is "npm"? npm is Node's package manager — it downloads other people's JavaScript code (like express or bcrypt) into a folder called node_modules so your own code can use it. npm install does the downloading; npm run dev runs a named shortcut command listed in package.json.
02

Variables — boxes with labels

A variable is just a named box holding a value. This project only ever uses two ways to create one:

✓ const

The label is permanent — you can't reassign it later. Used for almost everything here, because almost nothing needs to change after it's created.

const salt = await bcrypt.genSalt(12);

✓ let

Same as const, but the value can be reassigned later. Rare in this codebase — most values are set once and never changed.

You may see an older codebase use var instead — this project deliberately never does. var has confusing rules about where it's visible; const/let fixed that, so modern code just doesn't use var anymore.

The data types you'll actually see here

  • String — text, always in quotes: 'client', "Registration failed"
  • Number — 12 in bcrypt.genSalt(12), no quotes
  • Boolean — true / false, e.g. required: true in User.js
  • Object — a labeled bundle of values, e.g. { id: user._id, role: user.role } — its own section below
  • undefined / null — "nothing here." A variable that was never given a value is undefined.
03

Functions — reusable steps

A function is a named block of steps you can run whenever you need them, optionally feeding it inputs. This codebase almost exclusively uses arrow functions — a shorter way to write a function, using =>.

backend/src/utils/token.js
const generateToken = (user) => {
  return jwt.sign(
    { id: user._id, role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: process.env.JWT_EXPIRES_IN }
  );
};
  • generateToken is the name — the label you call it by elsewhere.
  • (user) is the input it expects — here, one value called user.
  • => means "goes to" / "produces" — everything after it is what the function does.
  • { ... } after the arrow is the function's body — the actual steps, wrapped in curly braces.
  • return hands a value back to whoever called the function.

Why arrow functions specifically? not just style

Two real reasons this project uses them everywhere:

Older style

function generateToken(user) {
  return jwt.sign(/* ... */);
}

Arrow style (used here)

const generateToken = (user) => {
  return jwt.sign(/* ... */);
};

Both do the same thing for a simple case like this. The real payoff shows up with this-binding in class-based code (not really used here) and, more relevantly, brevity when passing a function straight into another function — which is exactly what Express route handlers and middleware are:

backend/src/server.js
app.get('/api/health', (req, res) => {
  res.status(200).json({ status: 'ok' });
});

Here, the whole (req, res) => { ... } is an anonymous (unnamed) arrow function, created right where it's needed and handed directly to app.get as "the code to run when this route is hit."

04

Objects & destructuring

An object bundles related values under labels (called "keys"), like a small form:

{ name: 'Test User', email: 'test@example.com', role: 'client' }

Every incoming API request body arrives as an object like this. Destructuring is the shorthand this project uses everywhere to pull specific fields straight out of one:

backend/src/controllers/auth.controller.js
const { name, email, password, role } = req.body;

Without destructuring, the same line would be written four times over:

const name = req.body.name;
const email = req.body.email;
const password = req.body.password;
const role = req.body.role;

Both do exactly the same thing — the destructured version just says "pull these four named fields out of req.body, and make each one its own variable" in one line.

Dot access, the other way to reach into an object

You'll also see the plain form throughout the codebase, when only one field is needed:

user._id
user.name
user.passwordHash
req.user.id

object.key always means "give me the value stored at this label."

The shorthand property trick

backend/src/models/User.js → used in the controller
const existing = await User.findOne({ email });

This is shorthand for { email: email } — when a variable's name and the key you want match exactly, JavaScript lets you write it once instead of twice.

05

Template strings — text with variables mixed in

Backtick strings (using ` instead of ' or ") let you drop a variable straight into text using ${ }:

backend/src/server.js
console.log(`Server running on https://localhost:${PORT}`);

Whatever PORT holds (here, 5000) gets inserted right into the sentence, producing: Server running on https://localhost:5000. The alternative, without templates, is uglier string-gluing with +:

console.log('Server running on https://localhost:' + PORT);
06

Modules — how files share code

Every file in backend/src/ is its own sealed box. Nothing inside it is visible to any other file unless it's explicitly exported — and nothing from another file is usable unless it's explicitly imported. Two keywords do this: require and module.exports.

backend/src/utils/token.js — the exporting side
const generateToken = (user) => { /* ... */ };

module.exports = { generateToken };
backend/src/controllers/auth.controller.js — the importing side
const { generateToken } = require('../utils/token');

Read the second line the same way you now read destructuring: "run token.js, take the object it exports, and pull out just generateToken from it." The '../utils/token' part is a relative file path — ../ means "go up one folder first."

Two shapes of export, both used in this project:
  • module.exports = { register, login, getMe } — exports several named things at once (an object of them). Import with { } destructuring, like above.
  • module.exports = protect — exports one single thing directly, no wrapper object. Import it plain: const protect = require('../middleware/auth.middleware'), no curly braces.
07

async / await — waiting for slow things

Checking a database, hashing a password, or calling an external API all take real time — milliseconds, but not instant. JavaScript doesn't want to freeze everything else while it waits, so slow operations return a Promise: an "I'll get back to you" placeholder for a value that isn't ready yet.

await is how you say "pause this function right here until that promise resolves, then continue with the real value." You're only allowed to use await inside a function marked async — which is why almost every controller function in this project starts with exactly that word:

backend/src/controllers/auth.controller.js
const login = async (req, res, next) => {
  try {
    const { email, password } = req.body;

    const user = await User.findOne({ email });
    if (!user) {
      return res.status(401).json({ message: 'Invalid credentials' });
    }

    const match = await bcrypt.compare(password, user.passwordHash);
    if (!match) {
      return res.status(401).json({ message: 'Invalid credentials' });
    }

    const token = generateToken(user);
    return res.status(200).json({ token });
  } catch (err) {
    next(err);
  }
};
  • async (req, res, next) => — marks this whole function as one that's allowed to await things inside it.
  • await User.findOne({ email }) — "go ask MongoDB for a user with this email, and don't run the next line until the answer comes back."
  • await bcrypt.compare(...) — same idea: hashing comparison takes a moment, so we wait for the real true/false result before checking it.
  • generateToken(user) has no await — because signing a JWT is fast, synchronous math, not something that needs waiting for.
The mental model that actually matters: without await, const user = User.findOne({ email }) would hand you the unfinished promise itself, not the user — and every line after it would be working with "a promise that a user is coming," not an actual user object. await is what unwraps the promise into the real value.
08

try / catch — expecting things to go wrong

try runs a block of code optimistically. If anything inside it throws an error — a network failure, a bad database query, anything — execution immediately jumps into catch, skipping the rest of try, instead of crashing the whole server.

Pattern repeated in every controller function
try {
  // the real logic — database calls, hashing, etc.
} catch (err) {
  next(err);
}

next(err) is an Express-specific move: it hands the error off to the app's central error handler (in server.js) instead of dealing with it locally. That's what guarantees every possible failure — no matter which controller it came from — ends up producing the exact same safe, generic response:

backend/src/server.js
app.use((err, req, res, next) => {
  console.error(err.stack); // stays on the server only
  res.status(err.status || 500).json({ message: 'Something went wrong' });
});

A function with four parameters like this one is how Express specifically recognizes "this is the error handler" — it's always the last piece of middleware, and it's the only kind allowed to take err as its first argument.

09

npm packages & JSON

Every require('something') that isn't a relative path (doesn't start with ./ or ../) is pulling in code someone else wrote, downloaded into node_modules by npm install:

const bcrypt = require('bcrypt');       // password hashing
const jwt = require('jsonwebtoken');    // JWT sign/verify
const express = require('express');    // the web server framework itself
const mongoose = require('mongoose');   // talks to MongoDB

package.json keeps the official list of which packages (and which versions) the project depends on, so anyone who clones the repo can run npm install and get the exact same set.

JSON — the shape every API response takes

JSON looks almost identical to a JavaScript object, because it's based on the same syntax — but it's actually just text, used to send data between the browser/Postman and the server. res.json({...}) converts a real JavaScript object into that text form automatically:

res.status(201).json({
  id: user._id,
  name: user.name,
  email: user.email,
  role: user.role,
});

This is exactly what you see appear in a Postman response body — the object above, serialized as JSON text.

Putting it all together

Every idea above, all at once, in the real function that runs when someone registers. Read it now and it should actually make sense line by line.

backend/src/controllers/auth.controller.js
const register = async (req, res, next) => {
  try {
    const { name, email, password, role } = req.body;

    const existing = await User.findOne({ email });
    if (existing) {
      return res.status(400).json({ message: 'Registration failed' });
    }

    const salt = await bcrypt.genSalt(12);
    const passwordHash = await bcrypt.hash(password, salt);

    const user = await User.create({
      name,
      email,
      passwordHash,
      role: role || 'client',
    });

    return res.status(201).json({
      id: user._id,
      name: user.name,
      email: user.email,
      role: user.role,
    });
  } catch (err) {
    next(err);
  }
};

  1. Function & async

    async (req, res, next) => — an arrow function that's allowed to await. Express calls this automatically whenever a POST /api/auth/register request arrives.

  2. try, in case anything below fails

    Everything real happens inside try; any thrown error skips straight to catch at the bottom.

  3. Destructure the request body

    const { name, email, password, role } = req.body pulls four named fields out of the incoming JSON object in one line.

  4. Await the database check

    await User.findOne({ email }) pauses here until MongoDB answers whether this email is already registered.

  5. Early return on failure

    If a match was found, respond immediately with a generic 400 and stop — nothing below this line runs.

  6. Hash the password (two awaits)

    Generating a salt and hashing the password are both slow, asynchronous operations — each gets its own await.

  7. Create the user

    User.create({...}) saves the new document to MongoDB — note passwordHash is stored, and the real password variable is never saved anywhere.

  8. Respond with JSON

    An object is built up and handed to res.json(), which turns it into the JSON text Postman displays — deliberately leaving passwordHash out of it.

  9. catch, just in case

    If anything above threw — a lost database connection, an unexpected error — next(err) routes it to the one central handler that always replies the same safe way.

Cheat sheet

const x = ...
Create a variable that can't be reassigned.
(a, b) => { }
An arrow function taking inputs a and b.
{ a, b } = obj
Destructuring — pull fields a and b out of an object into their own variables.
`text ${x}`
Template string — inserts the variable x into the text.
require('x')
Import code from another file or an installed package.
module.exports
What a file makes available to other files that require it.
async / await
Wait for a slow operation (database, hashing, network) to finish before continuing.
try / catch
Run code optimistically; jump to catch if anything inside throws.
req / res
The incoming request and the outgoing response, in every Express route.
.json({...})
Send a JavaScript object back to the client as JSON text.
